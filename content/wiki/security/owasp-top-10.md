## OWASP Top 10이란

**OWASP**(Open Worldwide Application Security Project)는 웹 보안을 연구하는 비영리 단체다.
**Top 10**은 실제 취약점 데이터와 전문가 설문을 바탕으로 웹 애플리케이션에서 가장 중요한 보안 위험 10가지를 뽑은 목록이다.
몇 년마다 새로 나오며, 지금 최신판은 **2025년판**이다(2025년 11월 공개, 2021년판 다음).

취약점 하나하나가 아니라 **위험의 분류(카테고리)**라는 점을 기억해두자. 예를 들어 SQL 인젝션은 A05 Injection 안에 들어가는 한 종류다.

| **A04** | Cryptographic Failures | 민감한 데이터를 암호화하지 않거나 약하게 한다 |
| **A05** | Injection | 입력값이 명령이나 쿼리로 실행된다 |
| **A06** | Insecure Design | 설계 단계부터 보안 고려가 빠져 있다 |

### 2021년판과 달라진 점

- **A03 공급망 실패**와 **A10 예외 상황 처리 실패**가 새로 들어왔다.
- 2021년판의 A10이던 **SSRF**(서버가 공격자 대신 내부 주소로 요청을 보내게 만드는 것)는 A01 접근 제어 실패에 합쳐졌다.
- 보안 설정 오류가 5위에서 2위로 올라왔다.

## A01. Broken Access Control (접근 제어 실패)

로그인은 했지만 **내 권한 밖의 데이터나 기능**에 접근할 수 있는 문제다. 가장 흔하게 발견되는 위험이다.

- **예:** 주소의 `id=5`를 `id=6`으로 바꾸면 남의 주문 내역이 보인다([[idor]]), 일반 사용자가 `/admin` 주소로 바로 들어갈 수 있다, 서버가 사용자가 준 URL로 요청을 보내 내부망에 접근된다(SSRF)
- **방어:** 권한 검사는 **서버에서 요청마다** 하자. 기본은 거부(deny by default)로 두고 필요한 것만 허용하는 것이 좋다. 화면에서 버튼을 숨기는 것만으로는 막을 수 없다.

## A02. Security Misconfiguration (보안 설정 오류)

코드는 괜찮은데 **설정**이 잘못된 경우다.

- **예:** 기본 관리자 계정·비밀번호를 그대로 둠, 운영 서버에서 디버그 모드를 켜 둠(오류 화면에 코드와 경로가 노출), 클라우드 저장소를 누구나 읽을 수 있게 열어 둠, `.git`·`.env` 같은 파일이 웹에서 다운로드됨([[웹-정찰]])
- **방어:** 쓰지 않는 기능과 계정은 끄고, 운영 환경 설정을 따로 관리하자. 설정 점검 목록을 만들어 배포할 때마다 확인하면 된다.

## A03. Software Supply Chain Failures (소프트웨어 공급망 실패)

내가 짠 코드가 아니라 **가져다 쓴 것**에서 생기는 문제다. 2021년판의 "취약하고 오래된 구성요소"를 넓힌 항목이다.

- **예:** 알려진 취약점이 있는 옛 버전 라이브러리를 계속 사용, 이름이 비슷한 가짜 패키지를 설치(타이포스쿼팅), 빌드·배포 도구가 해킹되어 악성 코드가 섞임
- **방어:** 의존성 버전을 고정(lock 파일)하고, `npm audit`나 GitHub Dependabot 같은 도구로 취약점을 확인하자. 패키지는 공식 저장소에서 이름을 확인하고 설치하는 것이 좋다.

## A04. Cryptographic Failures (암호화 실패)

민감한 데이터를 **암호화하지 않거나, 약한 방식으로** 보호하는 문제다.

- **예:** HTTPS 없이 로그인 정보를 전송, 비밀번호를 평문이나 MD5·SHA-1 해시로 저장, 암호화 키를 코드에 직접 적어 둠
- **방어:** 전송은 HTTPS, 비밀번호는 bcrypt·Argon2 같은 비밀번호 전용 해시를 쓰자. 키와 비밀값은 코드 밖에서 관리하면 된다([[env로-api-키-관리]]).
- **주의:** Base64는 **인코딩이지 암호화가 아니다.** 누구나 되돌릴 수 있다([[인코딩과-디코딩]]).

## A05. Injection (인젝션)

사용자 입력이 **데이터가 아니라 명령의 일부로** 해석되어 실행되는 문제다.

- **예:** SQL 인젝션([[sql-인젝션]]), OS 명령어 인젝션, XSS(입력한 스크립트가 다른 사용자 브라우저에서 실행됨)
- **방어:** 입력을 문자열로 이어 붙이지 말고 **파라미터 바인딩**(prepared statement)을 쓰자. 화면에 출력할 때는 이스케이프하고, 입력값은 허용 목록으로 검증하는 것이 좋다.
- **참고:** LLM에서 비슷한 문제가 [[프롬프트-인젝션]]이다. 지시와 데이터가 섞인다는 원리가 같다.

## A06. Insecure Design (안전하지 않은 설계)

구현 실수가 아니라 **설계 자체**에 빈틈이 있는 문제다. 코드를 아무리 잘 짜도 고칠 수 없다.

- **예:** 비밀번호 찾기를 "좋아하는 색은?" 같은 질문으로만 확인, 쿠폰·결제 요청에 횟수 제한이 없어 무한 반복 가능, 단계별 절차를 건너뛰고 마지막 단계 요청만 보내도 처리됨([[ctf-문제-설계#진행-상태는-서버가-관리|CTF 문제 설계]]에서 막은 방법)
- **방어:** 기능을 만들기 전에 "이걸 악용하면 어떻게 되지?"를 먼저 생각해보자(위협 모델링). 남용 시나리오를 테스트 케이스로 만들어 두면 좋다.

## A07. Authentication Failures (인증 실패)

**로그인과 세션 관리**가 허술한 문제다.

- **예:** 무차별 대입 공격(brute force)을 막지 않음, `1234` 같은 약한 비밀번호 허용, 로그아웃해도 세션이 계속 유효함, 세션 ID가 URL에 노출됨
- **방어:** 로그인 실패 횟수를 제한하고, 가능하면 다중 인증(MFA)을 쓰자. 세션은 로그인할 때 새로 발급하고 로그아웃할 때 서버에서 끝내면 된다([[flask-세션]]).

## A08. Software or Data Integrity Failures (무결성 실패)

**변조되지 않았는지 확인하지 않고** 코드나 데이터를 믿는 문제다.

- **예:** 서명 확인 없이 자동 업데이트를 받음, 외부 CDN 스크립트를 무결성 검사 없이 불러옴, 사용자가 보낸 직렬화 데이터를 그대로 역직렬화함(Python `pickle` 등)
- **방어:** 업데이트와 패키지는 서명이나 해시로 확인하자. 외부 스크립트에는 SRI(`integrity` 속성)를 붙이고, 믿을 수 없는 데이터는 역직렬화하지 않는 것이 좋다.

## A09. Security Logging and Alerting Failures (로깅·알림 실패)

공격을 당해도 **기록이 없거나, 기록은 있는데 아무도 모르는** 문제다. 이름이 "Monitoring"에서 "Alerting"으로 바뀌었는데, 로그를 남기는 것만으로는 부족하고 알림까지 가야 한다는 뜻이다.

- **예:** 로그인 실패가 수천 번 반복되어도 기록이 없음, 로그는 있지만 아무도 보지 않음, 로그에 비밀번호나 개인정보를 그대로 남김
- **방어:** 로그인, 권한 실패, 중요한 변경은 기록하고 이상한 패턴에는 알림을 걸자. 로그에 민감한 정보는 남기지 않도록 하자.

## A10. Mishandling of Exceptional Conditions (예외 상황 처리 실패)

**오류나 예상 못한 상황**에서 시스템이 안전하지 않게 동작하는 문제다. 2025년판에 새로 생긴 항목이다.

- **예:** 오류가 나면 권한 검사를 건너뛰고 통과시킴(fail open), 오류 메시지에 내부 경로·쿼리가 그대로 노출, 결제 도중 오류가 나서 돈은 빠졌는데 처리가 반쯤만 됨, 큰 입력으로 메모리·디스크가 바닥남
- **방어:** 오류가 나면 **거부하는 쪽으로** 끝나게 하자(fail closed). 사용자에게는 일반적인 오류 메시지만 보여주고, 여러 단계 작업은 트랜잭션으로 묶어 중간에 실패하면 되돌리면 된다.
