## BaaS란

**BaaS(Backend as a Service)**는 서버 쪽 기능(데이터베이스, 로그인, 파일 저장 등)을 **직접 만들지 않고 서비스로 빌려 쓰는** 방식이다. 대표적으로 구글의 **Firebase**와 오픈소스인 **Supabase**가 있다.

보통의 웹 서비스는 [[http-통신과-3계층-구조|3계층 구조]]로 만든다. 앱과 DB 사이에 **내가 만든 서버**가 있고, 서버가 요청을 검사한 뒤 DB에 접근한다.
BaaS를 쓰면 그 서버를 만들지 않는다. **앱이 BaaS가 제공하는 API로 DB에 직접** 요청한다.

```text
직접 만든 서버        앱 ──▶ 내 서버 (Flask 등) ──▶ DB
                            └ 권한 검사, 입력 검증을 여기서 한다

BaaS (Supabase)      앱 ──▶ Supabase API ──▶ PostgreSQL
                                             └ 권한 검사를 DB의 RLS가 한다
```

| 장점 | 단점 |
| --- | --- |
| 서버 코드 없이 바로 DB·로그인을 쓸 수 있다 | 권한 설계를 잘못하면 **DB가 그대로 열린다** |
| 서버 운영(배포, 보안 업데이트)을 신경 쓰지 않아도 된다 | 복잡한 처리는 결국 서버 함수가 필요하다 |
| 무료 플랜으로 작은 프로젝트를 시작하기 좋다 | 서비스 정책과 요금에 묶인다 |

## Supabase의 구성

Supabase는 PostgreSQL 데이터베이스를 중심으로 여러 기능을 묶은 것이다.

| 기능 | 하는 일 |
| --- | --- |
| **Database** | PostgreSQL. 테이블을 만들면 **REST API가 자동으로** 생긴다 |
| **Auth** | 회원가입·로그인. 이메일, 소셜 로그인 등. 로그인하면 토큰(JWT)을 준다 |
| **Storage** | 이미지 같은 파일 저장 |
| **Realtime** | DB가 바뀌면 앱에 바로 알려준다 |
| **Edge Functions** | 서버에서 돌아가는 작은 함수. 비밀 키가 필요한 일은 여기서 한다 |

### 앱에서 쓰는 모습

스쿨헬퍼(Flutter)에서 공지를 가져오는 코드다. SQL을 쓰지 않고 메서드를 이어 붙여 조회한다.

```dart
final notices = await client
    .from('notice')
    .select()
    .or('grade.is.null,and(grade.eq.$myGrade,class.eq.$myClass)')  // 전체 공지 + 내 반 공지
    .order('is_pinned', ascending: false)                          // 고정 먼저
    .order('created_at', ascending: false);                        // 최신 순
```

이 코드는 결국 Supabase API로 가는 [[http와-https|HTTPS]] 요청이 되고, Supabase가 SQL로 바꿔 PostgreSQL에 실행한다.

## 공개 키는 비밀이 아니다

Supabase 프로젝트에는 키가 두 종류 있다. 둘의 차이를 아는 것이 가장 중요하다.

| 키 | 예전 이름 | 넣는 곳 | 권한 |
| --- | --- | --- | --- |
| **Publishable key** (공개 키) | anon key | **앱 안** | 로그인 안 한 사용자 수준. RLS 정책을 따른다 |
| **Secret key** (비밀 키) | service_role key | **서버에만** | 모든 권한. **RLS를 무시한다** |

공개 키는 앱 안에 그대로 들어간다. 앱 파일을 풀어 보면 누구나 꺼낼 수 있다. 웹이라면 개발자 도구에서 바로 보인다.
그래서 공개 키는 처음부터 **"알려져도 되는 키"**로 설계되어 있다. 이 키로 할 수 있는 일은 RLS 정책이 허락한 것뿐이다.

이 말은 거꾸로, **RLS를 켜지 않으면 공개 키를 가진 누구나 DB를 마음대로 할 수 있다**는 뜻이다.

- 스쿨헬퍼 첫 버전이 그랬다. 공지 테이블에 RLS가 꺼져 있었고, 익명 사용자에게 쓰기·삭제 권한이 있었다. 앱 화면에서는 임원만 공지를 쓸 수 있는 것처럼 보였지만, 공개 키로 직접 요청하면 누구나 모든 공지를 지울 수 있었다.
- 고친 방법은 [[rls와-접근-제어]]에 있다.

비밀 키는 반대로 **절대 앱에 넣으면 안 된다.** 앱에 들어간 순간 공개된 것과 같다. 비밀 키가 필요한 일(관리 작업, 다른 유료 API 호출)은 Edge Function이나 직접 만든 서버에서 한다. → [[env로-api-키-관리]]

## 로그인과 토큰

1. 앱이 Auth에 아이디·비밀번호를 보낸다.
2. 맞으면 Auth가 **액세스 토큰(JWT)**을 준다. 토큰에는 사용자 ID와 만료 시각이 서명되어 있다.
3. 앱은 이후 모든 요청에 이 토큰을 `Authorization` 헤더로 붙인다. Supabase 라이브러리가 자동으로 해 준다.
4. PostgreSQL은 토큰에서 사용자 ID를 꺼내 RLS 정책의 `auth.uid()`로 쓴다.

토큰은 서명되어 있어서 사용자가 내용을 고칠 수 없다. 그래서 RLS가 토큰의 사용자 ID를 믿고 권한을 판단할 수 있다. 서명의 원리는 [[대칭키와-공개키-암호#용도-2-전자-서명|전자 서명]]과 같다.

### 아이디로 로그인하기

Supabase Auth는 기본적으로 **이메일**로 계정을 만든다. 스쿨헬퍼는 학생 임원에게 이메일을 받지 않으려고, 앱이 아이디를 내부용 이메일 형식으로 바꿔서 보낸다.

```text
사용자가 입력: minsu
앱이 보내는 값: minsu@<내부용 도메인>
```

- 사용자에게는 이메일이 보이지 않는다.
- 아이디는 영문·숫자·`_`만 허용하고 소문자로 맞춘다. 같은 사람이 대소문자만 다른 계정을 만드는 일을 막는다.
- 회원가입 화면은 만들지 않았다. 임원 계정은 관리자가 SQL로 만든다. 그래서 Supabase 설정에서 **공개 회원가입을 꺼야** 한다. 켜 두면 누구나 Auth 계정을 만들 수 있다. 물론 임원 명단(`executives`)에 없으면 권한은 없다.

## 무료 플랜에서 주의할 점

- **일시 정지:** 일정 기간(약 1주일) 사용이 없으면 프로젝트가 자동으로 멈춘다. 대시보드에서 다시 켜야 한다. 방학 동안 아무도 앱을 안 쓰면 개학 날 앱이 안 될 수 있다.
- **백업과 브랜치:** 무료 플랜은 백업과 DB 브랜치 기능이 제한된다. 스쿨헬퍼는 그래서 DB 변경을 마이그레이션 하나씩, 적용 전에 확인하고 진행했다.
- **용량 제한:** DB 크기, 파일 저장 용량, 월 활성 사용자 수에 한도가 있다.

## 처음 쓸 때 점검할 것

- [ ] 앱에는 **공개 키만** 넣었는가
- [ ] 모든 테이블에 RLS를 켰는가 (SQL로 만든 테이블은 기본으로 꺼져 있을 수 있다)
- [ ] 회원가입을 쓰지 않는다면 공개 회원가입을 껐는가
- [ ] 대시보드의 Security Advisor 경고를 확인했는가
- [ ] 비밀 키가 Git에 올라가지 않았는가
