## 온톨로지란

**온톨로지(Ontology)**는 원래 철학에서 "무엇이 존재하는가, 존재하는 것들은 어떤 종류로 나뉘는가"를 묻는 분야(존재론)를 가리키는 말이다.

컴퓨터 분야에서는 뜻이 조금 달라진다. 어떤 분야에 **어떤 개념이 있고, 그 개념들이 서로 어떤 관계인지**를 정해둔 설계도를 말한다.
사람끼리는 말하지 않아도 아는 "학생은 사람이다" 같은 상식을, 컴퓨터도 알 수 있도록 **명시적으로 적어두는 것**이 핵심이다.

## 구성 요소

대학을 예로 들면 다음과 같다.

| 구성 요소 | 뜻 | 예 |
| --- | --- | --- |
| **클래스** | 개념의 종류 | 사람, 학생, 교수, 강의 |
| **계층** | 상위·하위 관계 | 학생 **은 일종의** 사람 |
| **속성** | 개념이 가지는 값 | 학생은 학번을 가진다 |
| **관계** | 개념과 개념 사이의 연결 | 교수 **가르친다** 강의, 학생 **수강한다** 강의 |
| **규칙** | 반드시 지켜야 하는 조건 | 강의에는 교수가 최소 한 명 있어야 한다 |
| **인스턴스** | 실제 데이터 | 민수(학생)가 "자료구조"(강의)를 수강한다 |

클래스·계층·속성·관계·규칙이 **틀**이고, 인스턴스는 그 틀에 채워지는 **실제 내용**이다.

## 추론

온톨로지를 쓰는 가장 큰 이유는 컴퓨터가 **적혀 있지 않은 사실을 알아낼 수 있다**는 점이다.

- "민수는 학생이다" + "학생은 사람이다" → **민수는 사람이다**
- "김 교수가 자료구조를 가르친다" + "민수가 자료구조를 수강한다" → **민수는 김 교수의 수업을 듣는다**
- "강의에는 교수가 최소 한 명 있어야 한다"인데 교수가 없는 강의가 있다 → **데이터 오류**를 찾아낸다

사실을 하나하나 다 적지 않아도 되고, 규칙에 어긋나는 데이터를 자동으로 걸러낼 수 있다.

## 비슷한 개념과의 차이

| 개념 | 하는 일 | 예 |
| --- | --- | --- |
| **분류 체계(택소노미)** | 상하 관계만 있는 트리 | 생물 분류(계·문·강·목…), 쇼핑몰 카테고리 |
| **온톨로지** | 상하 관계에 더해 여러 종류의 관계와 규칙까지 정의 | 의료 용어 표준 |
| **지식 그래프** | 온톨로지라는 틀에 실제 데이터를 채운 그래프 | 위키데이터, 검색 결과 옆의 인물 정보 상자 |
| **DB 스키마** | 데이터를 **어떻게 저장할지** 정한 구조 | 테이블과 열 정의 |

분류 체계는 "무엇이 무엇의 한 종류인가"만 말한다. 온톨로지는 "무엇이 무엇과 **어떻게** 관련되는가"까지 말한다.
DB 스키마는 저장과 조회를 위한 구조이고, 온톨로지는 데이터가 **무슨 뜻인지**를 정의하는 데 초점이 있다. 그래서 서로 다른 DB를 하나로 합칠 때 "이쪽의 `고객`과 저쪽의 `회원`은 같은 개념"이라고 연결하는 용도로도 쓴다.

## 표현하는 방법

온톨로지는 W3C가 정한 표준 형식으로 적는 경우가 많다.

| 형식 | 역할 |
| --- | --- |
| **RDF** | 모든 사실을 **주어–서술어–목적어** 세 칸(트리플)으로 표현한다 |
| **RDFS** | RDF에 클래스·상하 관계 같은 기본 어휘를 더한다 |
| **OWL** | "서로 겹치지 않는 클래스", "최소 한 명" 같은 더 세밀한 규칙을 표현한다 |
| **SPARQL** | RDF 데이터를 조회하는 질의 언어 (DB의 SQL에 해당) |

RDF 트리플은 이런 모양이다.

```text
민수      종류      학생
학생      하위개념   사람
민수      수강      자료구조
```

이 트리플들은 실제로는 [[xml|XML]]이나 JSON-LD([[json|JSON]] 기반) 같은 [[데이터-형식]]으로 저장한다.

## 어디에 쓰이나

- **검색과 지식 그래프:** 검색 엔진이 "이 단어는 사람 이름이고, 이 사람의 직업은 무엇"처럼 의미를 이해하는 데 쓴다.
- **의료:** 질병·증상·약 사이의 관계를 표준화한다(SNOMED CT, 유전자 온톨로지 등). 병원마다 다른 용어를 같은 개념으로 맞출 수 있다.
- **기업 데이터 통합:** 부서마다 따로 있는 데이터를 공통 개념으로 묶어 한 번에 조회한다.
- **AI와 함께:** LLM이 사실관계를 지어내지 않도록 지식 그래프에서 근거를 찾아 답하게 하는 방식(GraphRAG)에 쓰인다.

## 장단점

| 장점 | 단점 |
| --- | --- |
| 데이터의 뜻이 분명해져서 시스템끼리 맞추기 쉽다 | 처음 설계하는 데 시간과 전문 지식이 많이 든다 |
| 적지 않은 사실을 추론할 수 있다 | 분야가 바뀌거나 커지면 계속 고쳐야 한다 |
| 규칙으로 잘못된 데이터를 찾을 수 있다 | 규칙이 많아지면 추론이 느려진다 |

작은 프로젝트에서는 분류 체계나 DB 스키마로 충분한 경우가 많다. 온톨로지는 **여러 시스템과 사람이 같은 개념을 공유해야 할 때** 가치가 커진다.

## 이 위키와 비교하면

이 사이트의 [문서 지도](/graph)는 "어떤 문서가 어떤 문서와 이어져 있는가"만 보여준다. 선에는 의미가 없다.
온톨로지처럼 만든다면 선마다 의미를 붙이게 된다.

- [[sql-인젝션|SQL 인젝션]] **은 일종의** 인젝션 공격
- [[owasp-top-10#a05-injection-인젝션|OWASP A05]] **가 다룬다** SQL 인젝션
- 입력 검증 **이 막는다** 인젝션 공격

태그(`tags`)와 상위·하위 문서는 그중 가장 단순한 형태, 즉 분류 체계에 가깝다.
