## 기본 용어

| 용어 | 뜻 |
| --- | --- |
| **평문** | 원래 내용. 예: `안녕` |
| **암호문** | 알아볼 수 없게 바꾼 내용. 예: `x9#Qa2...` |
| **암호화 / 복호화** | 평문 → 암호문 / 암호문 → 평문 |
| **알고리즘** | 바꾸는 방법 (AES, RSA 등) |
| **키** | 알고리즘에 넣는 비밀 값. 같은 알고리즘이라도 키가 다르면 결과가 다르다 |

현대 암호는 **알고리즘을 공개**하고 **키만 비밀**로 지킨다. 이것을 케르크호프스의 원칙이라고 한다.
방법을 숨기는 암호는 방법이 새는 순간 끝난다. 공개된 알고리즘은 전 세계 전문가가 수십 년 동안 공격해 보고도 버틴 것이라 믿을 수 있다.

> [[인코딩과-디코딩|인코딩]](Base64 등)은 암호화가 아니다. 키가 없어서 누구나 되돌릴 수 있다. 형식을 바꾸는 것일 뿐이다.

## 대칭키 암호

**잠글 때와 열 때 같은 키**를 쓴다. 자물쇠와 열쇠 하나와 같다.

```text
평문 + 키 → 암호문
암호문 + 같은 키 → 평문
```

- **대표 알고리즘:** AES (가장 널리 쓰임), ChaCha20 (휴대폰처럼 AES 전용 하드웨어가 없는 기기에서 빠름)
- **장점:** 빠르다. 영상이나 대용량 파일도 실시간으로 암호화할 수 있다.
- **단점: 키를 어떻게 전하나?** 상대에게 키를 보내야 하는데, 그 키를 보내는 통신이 도청당하면 끝이다. 이것을 **키 배송 문제**라고 한다.
- 사람이 많아지면 키도 많이 필요하다. 100명이 서로 따로 비밀 대화를 하려면 100 × 99 ÷ 2 = 4,950개의 키가 필요하다.

## 공개키 암호

**키를 두 개 한 쌍으로** 만든다. 1970년대에 나온 생각으로, 암호의 역사를 바꿨다.

| 키 | 공개 여부 |
| --- | --- |
| **공개키** | 누구에게나 공개해도 된다 |
| **개인키** | 나만 가진다. 절대 밖으로 내보내지 않는다 |

한 키로 잠근 것은 **다른 쪽 키로만** 열린다. 공개키로부터 개인키를 계산해 내는 것은 현실적으로 불가능하다.

- **대표 알고리즘:** RSA (1977년), 타원곡선 암호(ECC: Ed25519, P-256 등)
- **장점:** 키 배송 문제가 없다. 공개키는 도청당해도 상관없다.
- **단점:** 대칭키보다 수백~수천 배 느리다. 큰 데이터를 직접 암호화하기에는 맞지 않다.

공개키 암호는 두 가지 방향으로 쓴다.

### 용도 1: 비밀 전달

```text
보내는 사람: 받는 사람의 공개키로 잠근다
받는 사람:   자기 개인키로 연다
```

누구나 잠글 수 있지만 **열 수 있는 사람은 개인키 주인뿐**이다. 누구나 넣을 수 있지만 주인만 열 수 있는 우체통과 같다.

### 용도 2: 전자 서명

```text
서명하는 사람: 자기 개인키로 서명을 만든다
확인하는 사람: 서명한 사람의 공개키로 확인한다
```

개인키가 없으면 그 서명을 만들 수 없다. 그래서 서명이 확인되면 **개인키 주인이 만든 것이 맞고, 그 뒤로 내용이 바뀌지 않았다**는 것이 증명된다.

- [[http와-https#인증서|HTTPS 인증서]]는 인증 기관이 "이 공개키는 이 도메인의 것"이라고 서명한 문서다.
- 프로그램의 **코드 서명**, 공동인증서, Git 커밋 서명도 같은 원리다.

## 키 교환: 디피-헬먼

공개키 암호로 대칭키를 안전하게 맞추는 대표적인 방법이 **디피-헬먼(Diffie-Hellman) 키 교환**이다. 1976년에 발표됐다.
특징은 **키를 보내지 않고도** 양쪽이 같은 키를 갖게 된다는 점이다.

물감 섞기로 비유하면 이렇다(실제로는 물감이 아니라 수학 계산이다).

```text
1. 둘이 공개된 노란색을 정한다.                       (모두가 봐도 됨)
2. 민수는 비밀 빨강, 지수는 비밀 파랑을 고른다.          (각자만 앎)
3. 민수: 노랑+빨강 = 주황을 보낸다.                    (도청자도 봄)
   지수: 노랑+파랑 = 초록을 보낸다.                    (도청자도 봄)
4. 민수: 받은 초록 + 자기 빨강 = 갈색
   지수: 받은 주황 + 자기 파랑 = 갈색                   (같은 색!)
```

도청자는 노랑, 주황, 초록을 모두 봤다. 하지만 섞인 물감에서 원래 색을 분리할 수 없어서 갈색을 만들지 못한다.
실제로는 "곱하기는 쉽지만 거꾸로 풀기는 매우 어려운" 수학 문제(이산 로그 문제)가 물감 섞기 역할을 한다.

### 전방 비밀성

요즘 HTTPS와 [[vpn|VPN]]은 연결할 때마다 **새 임시 키**로 디피-헬먼을 한다(ECDHE). 대화가 끝나면 그 키는 버린다.
그래서 나중에 서버의 개인키가 털려도, 예전에 녹음해 둔 암호 통신을 풀 수 없다. 이것을 **전방 비밀성(Forward Secrecy)**이라고 한다.

## 해시

**해시 함수**는 어떤 길이의 데이터든 **정해진 길이의 값**으로 바꾸는 함수다.

```text
SHA-256("안녕")  → e8f817f346d1d411... (64자리 16진수)
SHA-256("안녕.") → 52009c1cc96a80ff... (점 하나로 완전히 달라진다)
```

| 성질 | 뜻 |
| --- | --- |
| **일방향** | 해시 값으로부터 원래 데이터를 알아낼 수 없다. 암호화와 달리 **되돌리는 키가 없다** |
| **눈사태 효과** | 입력이 조금만 달라도 결과가 완전히 바뀐다 |
| **충돌 저항** | 같은 해시 값이 나오는 다른 데이터를 찾기 매우 어렵다 |

### 쓰는 곳

- **무결성 확인:** 파일을 내려받은 뒤 해시를 계산해서 배포처가 공개한 값과 비교한다. 다르면 파일이 바뀐 것이다. 웹의 SRI도 이 방식이다.
- **비밀번호 저장:** 서버는 비밀번호를 그대로 저장하지 않고 해시로 저장한다. 로그인할 때 입력값의 해시를 비교한다. DB가 털려도 원래 비밀번호가 바로 드러나지 않는다.
  - 단, SHA-256처럼 **빠른 해시는 비밀번호에 쓰면 안 된다.** 빠를수록 공격자가 1초에 수십억 개를 대입해 볼 수 있다.
  - 비밀번호에는 일부러 느리게 만든 **bcrypt, Argon2**를 쓴다. 사용자마다 다른 무작위 값(**솔트**)을 섞어서, 같은 비밀번호라도 해시 값이 다르게 나오게 한다.
- **전자 서명:** 긴 문서 전체가 아니라 문서의 해시에 서명한다.
- **Git:** 커밋마다 붙는 ID가 해시 값이다.

MD5와 SHA-1은 충돌을 만드는 방법이 발견되어 보안 용도로는 더 이상 쓰지 않는다.

### 메시지 인증과 AEAD

해시만으로는 공격자가 내용을 바꾸고 해시도 새로 계산해 붙이면 막을 수 없다. 그래서 **비밀 키를 섞은 해시**(MAC, HMAC)를 쓴다. 키를 모르는 사람은 올바른 값을 만들 수 없다.

요즘은 암호화와 무결성 확인을 한 번에 하는 **AEAD** 방식을 쓴다. AES-GCM, ChaCha20-Poly1305가 대표적이다. 암호문에 **인증 태그**가 붙어서, 한 비트라도 바뀌면 복호화 자체를 거부한다.

## 섞어서 쓴다: 하이브리드 암호

실제 통신은 대칭키와 공개키를 **섞어서** 쓴다. 공개키의 안전함과 대칭키의 빠름을 둘 다 얻기 위해서다.

| 단계 | 쓰는 것 | 하는 일 |
| --- | --- | --- |
| 1. 상대 확인 | 공개키 암호 (전자 서명, 인증서) | 진짜 서버인지 확인 |
| 2. 키 맞추기 | 디피-헬먼 키 교환 | 양쪽만 아는 세션 키 만들기 |
| 3. 데이터 보호 | 대칭키 암호 (AEAD) | 실제 데이터를 빠르게 암호화하고 변조 확인 |

[[http와-https#https|HTTPS]]와 [[vpn|VPN]](WireGuard, IPsec, OpenVPN)이 모두 이 구조다. 메신저의 종단 간 암호화도 마찬가지다.

## 알아둘 점

- **암호 알고리즘을 직접 만들지 않는다.** 아마추어가 만든 암호는 거의 반드시 뚫린다. 검증된 라이브러리를 쓴다.
- **안전한 무작위 값을 쓴다.** 키를 만들 때 일반 `random`이 아니라 암호용 난수 생성기(파이썬의 `secrets`)를 써야 한다. 일반 난수는 예측할 수 있다.
- **키 관리가 가장 어렵다.** 아무리 강한 암호도 키가 코드나 깃허브에 올라가면 소용없다. → [[env로-api-키-관리]]
- **양자 컴퓨터:** 충분히 큰 양자 컴퓨터가 나오면 RSA와 타원곡선 암호를 풀 수 있다. 그래서 이를 대비한 **양자 내성 암호**가 표준화됐다(미국 NIST, 2024년 ML-KEM 등). 최신 브라우저는 이미 기존 키 교환과 양자 내성 키 교환을 함께 쓰기 시작했다. 대칭키 암호(AES-256)와 해시는 키 길이만 충분하면 비교적 안전하다고 본다.
