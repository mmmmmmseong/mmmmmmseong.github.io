## 데이터베이스란

**데이터베이스(DB)**는 데이터를 **정해진 형식으로 모아 두고, 여러 사람이 동시에 안전하게 찾고 고칠 수 있게** 해 주는 저장소다.
데이터베이스를 관리하는 프로그램을 **DBMS**라고 한다. PostgreSQL, MySQL, SQLite가 대표적이다.

엑셀 파일과 비교하면 왜 필요한지 보인다.

| | 엑셀 파일 | 데이터베이스 |
| --- | --- | --- |
| 동시에 여러 명이 고치면 | 한 명이 저장하면 다른 사람 것이 덮어써진다 | 동시에 써도 섞이지 않는다 |
| 데이터가 많아지면 | 수십만 줄부터 느려진다 | 수억 줄에서도 원하는 것을 빠르게 찾는다 |
| 잘못된 값 | 아무 칸에나 아무 값이나 들어간다 | 규칙에 맞지 않는 값은 **거부**한다 |
| 권한 | 파일을 열 수 있으면 다 볼 수 있다 | 사람마다, 행마다 권한을 나눌 수 있다 |

앱이나 웹사이트의 회원 정보, 게시글, 주문 내역은 거의 다 데이터베이스에 들어 있다.

## 테이블, 행, 열

가장 많이 쓰는 **관계형 데이터베이스**는 데이터를 **표(테이블)**로 저장한다.

스쿨헬퍼의 공지 테이블(`notice`)을 단순하게 나타내면 이렇다.

| id | title | tag | grade | class | is_pinned | created_at |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 수학 수행평가 안내 | 수행평가 | 2 | 3 | true | 2026-11-17 |
| 2 | 체육대회 일정 | 행사 | NULL | NULL | false | 2026-11-18 |
| 3 | 청소 당번 변경 | 공지 | 2 | 3 | false | 2026-11-19 |

| 용어 | 뜻 | 위 표에서 |
| --- | --- | --- |
| **테이블** | 같은 종류의 데이터를 모은 표 | `notice` (공지) |
| **행** (row, 레코드) | 데이터 하나 | 공지 한 개 |
| **열** (column, 컬럼) | 데이터의 항목 | 제목, 태그, 학년 등 |
| **자료형** | 열에 들어갈 값의 종류 | 숫자, 글자, 참/거짓, 날짜 |

열마다 자료형이 정해져 있어서, `grade` 칸에 "이학년" 같은 글자를 넣으려고 하면 DB가 거부한다.

### NULL

**NULL**은 "값이 없음"을 뜻한다. 0이나 빈 글자(`""`)와 다르다.

- 위 표의 2번 공지는 학년과 반이 NULL이다. 특정 반이 아니라 **전체 공지**라는 뜻이다.
- NULL은 비교가 특이하다. `grade = NULL`이 아니라 `grade IS NULL`로 찾아야 한다. NULL은 "모르는 값"이라 다른 값과 같은지 다른지 판단할 수 없기 때문이다.
- 프로그래밍 언어의 `null`도 같은 뜻이다. 값이 없는데 있는 것처럼 쓰면 오류가 난다. → [[예외-처리#null]]

## 기본키와 외래키

- **기본키(Primary Key):** 각 행을 구분하는 **절대 겹치지 않는 값**. 위 표의 `id`다. 학교의 학번과 같다. 제목은 겹칠 수 있지만 id는 겹치지 않는다.
- **외래키(Foreign Key):** 다른 테이블의 기본키를 가리키는 값. 테이블과 테이블을 **연결**한다.

```text
executives (임원 명단)                    notice (공지)
  user_id = u-17   ◀──────────────────   author_id = u-17
  grade   = 2                             id        = 1
  class   = 3                             title     = 수학 수행평가 안내
  name    = 민수
```

공지의 `author_id`가 임원의 `user_id`를 가리킨다. 그래서 "1번 공지를 쓴 사람은 2학년 3반 민수"라는 것을 알 수 있다.
같은 정보를 여러 곳에 복사하지 않고 **키로 연결해서** 쓰는 것이 관계형 데이터베이스의 기본 방식이다. 민수의 반이 바뀌어도 임원 테이블 한 곳만 고치면 된다.

## SQL: 데이터베이스에 말하는 언어

관계형 데이터베이스는 **SQL**이라는 언어로 다룬다. 기본 동작은 네 가지다(머리글자를 따서 CRUD라고 부른다).

| 동작 | SQL | 예 |
| --- | --- | --- |
| **만들기** (Create) | `INSERT` | 공지 쓰기 |
| **읽기** (Read) | `SELECT` | 공지 목록 보기 |
| **고치기** (Update) | `UPDATE` | 공지 수정 |
| **지우기** (Delete) | `DELETE` | 공지 삭제 |

```sql
-- 2학년 3반 공지와 전체 공지를, 고정된 것 먼저, 최신 순으로
SELECT title, tag FROM notice
WHERE (grade = 2 AND class = 3) OR grade IS NULL
ORDER BY is_pinned DESC, created_at DESC;

-- 공지 쓰기
INSERT INTO notice (title, tag, grade, class) VALUES ('청소 당번 변경', '공지', 2, 3);

-- 3번 공지 제목 고치기
UPDATE notice SET title = '청소 당번 변경 (수정)' WHERE id = 3;

-- 3번 공지 지우기
DELETE FROM notice WHERE id = 3;
```

`UPDATE`와 `DELETE`에서 `WHERE`를 빠뜨리면 **모든 행**이 바뀌거나 지워진다. 가장 흔한 큰 실수다.

사용자가 입력한 글자를 SQL에 그대로 이어 붙이면 [[sql-인젝션]] 공격을 당한다. 값은 항상 따로 넘겨야 한다. → [[sqlite-기본#값은-항상-로|SQLite에서 값 넘기기]]

## 제약 조건

**제약 조건**은 "이 열에는 이런 값만 들어갈 수 있다"는 규칙이다. 규칙에 맞지 않는 값이 들어오면 DB가 저장을 거부한다.

| 제약 | 뜻 | 예 |
| --- | --- | --- |
| `NOT NULL` | 비워 둘 수 없다 | 제목은 반드시 있어야 한다 |
| `DEFAULT` | 값을 안 주면 넣을 기본값 | 태그를 안 주면 `공지` |
| `CHECK` | 조건을 만족해야 한다 | 학년은 1~3, 태그는 `수행평가`·`공지`·`행사` 중 하나 |
| `UNIQUE` | 다른 행과 겹칠 수 없다 | 아이디 |
| `PRIMARY KEY` | 기본키 (NOT NULL + UNIQUE) | `id` |
| `FOREIGN KEY` | 다른 테이블에 실제로 있는 값만 | 없는 임원을 작성자로 적을 수 없다 |

```sql
ALTER TABLE notice
  ADD CONSTRAINT grade_range CHECK (grade BETWEEN 1 AND 3),
  ADD CONSTRAINT grade_class_pair CHECK ((grade IS NULL) = (class IS NULL));
```

두 번째 규칙은 "학년과 반은 둘 다 비었거나, 둘 다 값이 있어야 한다"는 뜻이다.

### 앱에서 검사하면 되지 않나?

앱에서도 검사하지만, **DB에서 한 번 더** 막는 것이 안전하다.

- 앱에 버그가 있을 수 있다. 스쿨헬퍼는 앱이 태그 자리에 `null`을 직접 보내는 바람에 기본값 `공지`가 적용되지 않았다.
- 학년만 있고 반이 없는 공지가 들어가자, 어느 반 필터에도 걸리지 않아서 **아무에게도 보이지 않는 공지**가 생겼다.
- 앱이 여러 개(안드로이드, 웹, 관리 도구)여도 규칙은 DB 한 곳에만 있으면 된다.

## 인덱스

**인덱스**는 책 뒤의 **찾아보기**와 같다. "미적분"이 몇 쪽에 나오는지 처음부터 넘겨 보지 않고 찾아보기에서 바로 찾는다.

- 인덱스가 없으면 DB는 원하는 행을 찾으려고 **모든 행을 처음부터** 확인한다.
- 자주 검색하는 열(예: `grade`, `class`)에 인덱스를 만들면 빨라진다.
- 대신 데이터를 쓸 때마다 인덱스도 고쳐야 해서 쓰기가 조금 느려지고 공간을 더 차지한다. 그래서 필요한 곳에만 만든다.

공지가 수십 개일 때는 차이가 없다. 스쿨헬퍼도 "공지가 많아지면 추가"로 남겨 두었다.

## 트리거

**트리거**는 "어떤 일이 일어나면 자동으로 이것을 해라"라는 규칙이다.

스쿨헬퍼는 공지가 수정될 때마다 `updated_at`(수정 시각)을 자동으로 현재 시각으로 바꾸는 트리거를 쓴다. 앱이 수정 시각을 보내는 것을 깜빡해도 항상 정확하다.

## 트랜잭션

**트랜잭션**은 여러 작업을 **전부 성공하거나 전부 취소되는 한 묶음**으로 처리하는 것이다.

계좌 이체를 생각하면 쉽다.

```text
1. 민수 계좌에서 1만 원 빼기
2. 지수 계좌에 1만 원 넣기
```

1번만 되고 2번 전에 전원이 꺼지면 1만 원이 사라진다. 트랜잭션으로 묶으면, 2번이 실패할 때 1번도 **없던 일로 되돌린다(롤백)**. 둘 다 성공해야 확정한다(커밋).
코드에서 쓰는 방법은 [[sqlite-기본#트랜잭션과-연결-닫기]]에 있다.

## 마이그레이션

앱을 만들다 보면 테이블 구조를 바꿔야 한다. 열을 추가하거나, 제약을 넣거나, 새 테이블을 만든다.
**마이그레이션**은 이런 구조 변경을 **순서가 있는 단계로 기록해서** 적용하는 방법이다.

```text
001_create_notice.sql          공지 테이블 만들기
002_enable_rls.sql             보안 정책 켜기
003_add_constraints.sql        학년·반·태그 제약 추가
004_add_author_updated_at.sql  작성자, 수정 시각 열과 트리거 추가
```

- **이미 데이터가 있다는 점**이 핵심이다. 테이블을 지우고 새로 만들면 공지가 다 사라진다. 그래서 "기존 데이터를 살린 채 구조를 바꾸는" 단계를 쓴다.
- 제약을 추가하기 전에 **기존 데이터가 그 제약을 지키는지** 먼저 확인해야 한다. 학년만 있는 공지가 이미 있으면 제약 추가가 실패한다.
- 단계를 기록해 두면 다른 컴퓨터나 새 DB에도 똑같이 적용할 수 있다.
- 한 번에 하나씩 적용하고 확인한다. 스쿨헬퍼는 무료 플랜이라 백업이 없어서 특히 조심했다.

## 관계형과 NoSQL

모든 DB가 표 모양은 아니다.

| | 관계형 (SQL) | NoSQL |
| --- | --- | --- |
| 모양 | 표, 테이블끼리 연결 | 문서(JSON), 키-값 등 |
| 예 | PostgreSQL, MySQL, SQLite | Firebase Firestore, MongoDB, Redis |
| 장점 | 규칙과 관계가 분명하다 | 구조를 자유롭게 바꾸기 쉽다 |

대부분의 서비스는 관계형으로 시작한다. 스쿨헬퍼가 쓰는 Supabase도 관계형인 PostgreSQL이다.

## 자주 쓰는 DBMS

| DBMS | 특징 | 쓰는 곳 |
| --- | --- | --- |
| **SQLite** | 파일 하나가 DB. 설치할 서버가 없다 | 앱 안의 저장소, 작은 웹 서비스 → [[sqlite-기본]] |
| **PostgreSQL** | 기능이 많고 표준을 잘 지킨다. RLS 지원 | Supabase, 중·대형 서비스 |
| **MySQL / MariaDB** | 오래되고 널리 쓰인다 | 웹 호스팅, 많은 국내 서비스 |
