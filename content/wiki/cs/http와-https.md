## HTTP란

**HTTP(HyperText Transfer Protocol)**는 클라이언트와 서버가 **요청과 응답**을 주고받는 통신 규칙이다.
1991년 팀 버너스리가 웹 문서(하이퍼텍스트)를 주고받으려고 만들었다. 그래서 이름에 "하이퍼텍스트"가 들어 있다.
[[osi-7계층|OSI 7계층]]에서는 맨 위의 **응용 계층**에 속하고, 그 아래의 TCP(또는 QUIC) 위에서 동작한다.

```text
클라이언트 ──── 요청 ────▶ 서버
          ◀─── 응답 ─────
```

규칙은 단순하다.

- **클라이언트가 먼저 요청하고, 서버는 응답만 한다.** 서버가 먼저 말을 거는 일은 없다.
- **요청 하나에 응답 하나**가 짝을 이룬다.
- **무상태(Stateless):** 서버는 이전 요청을 기억하지 않는다. 같은 사람이 두 번 요청해도 서버 입장에서는 모르는 두 요청이다.

### 웹에서만 쓰이는 게 아니다

이름은 웹 문서용이지만, 지금은 **서버와 데이터를 주고받는 프로그램 대부분**이 HTTP를 쓴다.

| 분야 | 예 |
| --- | --- |
| **모바일 앱** | 날씨·배달·SNS 앱이 서버와 JSON을 주고받는 API 통신 → [[api-역공학]] |
| **프로그램끼리의 통신** | REST API, 웹훅(어떤 일이 생기면 다른 서버에 알려주기), 클라우드 서비스 SDK |
| **개발 도구** | `pip install`, `npm install`, `git clone https://...`, 도커 이미지 내려받기 |
| **업데이트와 다운로드** | 운영체제 업데이트, 게임 런처의 패치 파일, CDN의 파일 배포 |
| **동영상 스트리밍** | HLS, DASH. 영상을 작은 조각으로 나눠 HTTP로 받는다 |
| **실시간 통신의 시작점** | 웹소켓은 HTTP 요청으로 연결을 시작한 뒤 전환한다 |
| **서버 사이의 고속 통신** | gRPC는 HTTP/2 위에서 동작한다 |
| **DNS** | DNS over HTTPS(DoH). DNS 조회를 HTTPS로 감싸서 엿보지 못하게 한다 |
| **IoT 기기** | 공유기 설정 화면, 스마트 기기의 펌웨어 업데이트 |

다들 HTTP를 쓰는 이유는 다음과 같다.

- **방화벽을 잘 통과한다.** 회사나 학교 네트워크도 80·443번 포트는 거의 열어 둔다.
- **도구가 다 있다.** 언어마다 HTTP 라이브러리가 있고, `curl`이나 [[크롬-개발자-도구]]로 바로 확인할 수 있다.
- **인프라를 그대로 쓴다.** 웹용으로 만들어 둔 CDN, 캐시, 로드 밸런서, 인증서를 그대로 쓸 수 있다.
- **틀이 범용적이다.** 메서드, 상태 코드, 헤더라는 틀이 웬만한 통신에 다 맞는다.

## 요청과 응답의 구조

HTTP/1.1의 요청과 응답은 사람이 읽을 수 있는 **글자**로 되어 있다. 구조는 둘 다 같다.

```text
첫 줄          ← 요청: 메서드, 경로, 버전 / 응답: 버전, 상태 코드
헤더 여러 줄    ← 이름: 값
(빈 줄)        ← 헤더가 끝났다는 표시
본문           ← 실제 데이터 (없을 수도 있다)
```

### 요청

```http
POST /api/login HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 ...
Content-Type: application/json
Content-Length: 39

{"id": "minsu", "password": "abcd1234"}
```

- 첫 줄: `POST` 메서드로 `/api/login` 경로에 요청한다.
- `Host`: 어느 사이트에 보내는 요청인지 적는다. 서버 하나가 여러 사이트를 운영할 수 있어서 HTTP/1.1부터 필수다.
- 빈 줄 다음이 본문이다. 로그인 정보를 JSON으로 보낸다.

### 응답

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1256
Set-Cookie: session=8f3a...; HttpOnly; Secure
Cache-Control: max-age=3600

<!DOCTYPE html>
<html>...
```

- 첫 줄: 요청이 성공했다(`200 OK`).
- `Content-Type`: 본문이 UTF-8로 인코딩된 HTML이라고 알려준다.
- `Set-Cookie`: 브라우저에 쿠키를 저장하라고 한다. 다음 요청부터 브라우저가 이 값을 `Cookie` 헤더에 담아 보낸다.

## 메서드

요청이 **무엇을 하려는지** 나타낸다.

| 메서드 | 뜻 | 예 | 안전 | 멱등 |
| --- | --- | --- | --- | --- |
| **GET** | 조회 | 글 목록 보기 | O | O |
| **POST** | 생성, 처리 요청 | 글 쓰기, 로그인 | X | X |
| **PUT** | 전체 교체 | 글 전체 수정 | X | O |
| **PATCH** | 일부 수정 | 제목만 수정 | X | X |
| **DELETE** | 삭제 | 글 삭제 | X | O |
| **HEAD** | GET과 같지만 헤더만 받기 | 파일 크기만 확인 | O | O |
| **OPTIONS** | 서버가 허용하는 방식 묻기 | CORS 사전 요청 | O | O |

- **안전(Safe):** 서버의 데이터를 바꾸지 않는다. 그래서 검색 엔진 로봇이 GET 링크를 마음대로 눌러도 괜찮아야 한다. GET 요청으로 글을 삭제하게 만들면 안 되는 이유다.
- **멱등(Idempotent):** 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같다. 네트워크가 끊겨 응답을 못 받았을 때, 멱등한 요청은 그냥 다시 보내도 된다. POST는 두 번 보내면 글이 두 개 생길 수 있다.
- GET은 데이터를 URL의 쿼리(`?q=검색어`)에, POST는 본문에 담는다. URL은 브라우저 기록과 서버 로그에 남기 때문에 **비밀번호는 절대 GET 쿼리로 보내지 않는다.**

## 상태 코드

응답 첫 줄의 세 자리 숫자다. **첫 자리**만 봐도 대략 알 수 있다.

| 범위 | 뜻 | 자주 보는 코드 |
| --- | --- | --- |
| **1xx** | 처리 중 | 101 Switching Protocols (웹소켓 전환) |
| **2xx** | 성공 | 200 OK, 201 Created, 204 No Content |
| **3xx** | 다른 곳으로 가라 (리다이렉트) | 301 영구 이동, 302 임시 이동, 304 Not Modified (캐시 그대로 써라) |
| **4xx** | **클라이언트** 잘못 | 400 잘못된 요청, 401 로그인 필요, 403 권한 없음, 404 없음, 429 요청이 너무 많음 |
| **5xx** | **서버** 잘못 | 500 서버 내부 오류, 502 게이트웨이 오류, 503 일시적으로 사용 불가 |

- **401과 403의 차이:** 401은 "누군지 모르겠다(로그인해라)", 403은 "누군지는 아는데 권한이 없다"다.
- 4xx는 요청을 고쳐야 하고, 5xx는 서버를 고쳐야 한다. 문제가 생겼을 때 어느 쪽을 볼지 정하는 첫 단서다.
- 304는 [[캐싱과-캐시|캐시]]와 관련 있다. 브라우저가 "이 파일 바뀌었어?"라고 물으면 서버가 "안 바뀌었으니 가진 거 써"라고 답하고 본문을 보내지 않는다.

## 자주 쓰는 헤더

| 헤더 | 방향 | 하는 일 |
| --- | --- | --- |
| `Host` | 요청 | 요청하는 사이트의 도메인 |
| `User-Agent` | 요청 | 요청한 프로그램 정보 (브라우저 종류, 버전) |
| `Accept` | 요청 | 받고 싶은 데이터 형식 |
| `Content-Type` | 둘 다 | 본문의 형식(MIME 타입). 예: `application/json` → [[데이터-형식]] |
| `Content-Length` | 둘 다 | 본문 크기 (바이트) |
| `Cookie` / `Set-Cookie` | 요청 / 응답 | 쿠키 보내기 / 저장시키기 |
| `Authorization` | 요청 | 인증 정보 (API 키, 토큰) |
| `Cache-Control` | 둘 다 | 얼마나 오래 캐시할지 |
| `Location` | 응답 | 3xx 리다이렉트할 주소 |

## 무상태와 쿠키, 세션

HTTP는 무상태라서 서버는 방금 로그인한 사람을 다음 요청에서 기억하지 못한다. 그래서 상태를 이어 붙이는 방법을 따로 쓴다.

1. 로그인에 성공하면 서버가 `Set-Cookie`로 세션 번호를 준다.
2. 브라우저는 이후 모든 요청에 그 번호를 `Cookie` 헤더로 붙인다.
3. 서버는 번호를 보고 "아, 민수구나" 하고 알아본다.

자세한 구현은 [[flask-세션]]에 있다.

쿠키에는 보안 옵션을 붙인다.
- `HttpOnly`: 자바스크립트가 쿠키를 읽지 못하게 한다. XSS로 쿠키를 훔치는 것을 막는다.
- `Secure`: HTTPS로만 보낸다.
- `SameSite`: 다른 사이트에서 시작된 요청에는 쿠키를 보내지 않는다. CSRF 공격을 줄인다.

## URL의 구조

```text
https://example.com:443/wiki/search?q=http&page=2#results
```

| 부분 | 뜻 |
| --- | --- |
| **스킴** | 어떤 방식으로 통신할지. `http` 또는 `https` |
| **호스트** | 서버의 도메인이나 IP 주소 |
| **포트** | 생략하면 http는 80, https는 443 |
| **경로** | 서버 안에서 원하는 자원의 위치 |
| **쿼리** | `?` 뒤에 붙는 추가 조건. `이름=값`을 `&`로 잇는다 |
| **프래그먼트** | `#` 뒤. 페이지 안의 위치. **서버로 보내지 않고** 브라우저만 쓴다 |

경로와 쿼리를 도서관에 비유한 설명은 [[http-통신과-3계층-구조]]에 있다.

## HTTP의 버전

| 버전 | 나온 해 | 특징 |
| --- | --- | --- |
| HTTP/0.9 | 1991 | GET 하나뿐. HTML만 주고받았다 |
| HTTP/1.0 | 1996 | 헤더, 상태 코드, 이미지 같은 다양한 형식. 요청마다 TCP 연결을 새로 맺었다 |
| **HTTP/1.1** | 1997 | 연결 재사용(keep-alive), `Host` 필수. 오랫동안 표준으로 쓰였다 |
| **HTTP/2** | 2015 | 글자 대신 **바이너리**. 연결 하나로 여러 요청을 동시에 주고받는다(멀티플렉싱). 헤더 압축 |
| **HTTP/3** | 2022 | TCP 대신 UDP 위의 **QUIC**. 연결을 더 빨리 맺고, 패킷 하나가 늦어도 다른 요청이 기다리지 않는다 |

- HTTP/1.1에서는 한 연결에서 요청을 하나씩 순서대로 처리했다. 앞의 응답이 느리면 뒤의 요청이 모두 기다린다. 이것을 **HOL(Head-of-Line) 블로킹**이라고 한다. 그래서 브라우저는 사이트 하나에 연결을 6개쯤 동시에 열었다.
- HTTP/2는 연결 하나에서 여러 요청을 섞어 보내서 이 문제를 HTTP 수준에서 풀었다. 하지만 TCP는 패킷 하나가 빠지면 뒤의 데이터를 모두 붙잡아 둔다. 그래서 TCP 수준의 HOL 블로킹은 남았다.
- HTTP/3는 TCP를 버리고 QUIC으로 이 문제까지 풀었다.
- 버전이 바뀌어도 **메서드, 상태 코드, 헤더의 의미는 그대로**다. 바뀐 것은 이것을 실어 나르는 방식뿐이다.

## HTTPS

**HTTPS(HTTP Secure)**는 HTTP를 **TLS로 암호화한 것**이다. HTTP의 내용과 규칙은 그대로이고, 그 아래에 암호화 계층이 하나 끼어든다. 기본 포트는 443이다.

```text
HTTP  : HTTP → TCP → IP
HTTPS : HTTP → TLS → TCP → IP
```

TLS의 옛 이름은 SSL이다. SSL과 TLS 1.0·1.1은 보안 문제로 더 이상 쓰지 않고, 지금은 TLS 1.2와 1.3을 쓴다. 습관처럼 "SSL 인증서"라고 부르지만 실제로는 TLS다.

### 왜 필요한가

HTTP는 내용이 **그대로 보이는 글자**다. 같은 와이파이를 쓰는 사람, 공유기, 통신사 등 중간에 있는 누구나 볼 수 있다.

| 위협 | HTTP에서 일어나는 일 | HTTPS가 지켜주는 것 |
| --- | --- | --- |
| **도청** | 로그인 비밀번호, 쿠키가 그대로 보인다 | **기밀성:** 암호화해서 내용을 못 본다 |
| **변조** | 중간에서 페이지에 광고나 악성 코드를 끼워 넣는다 | **무결성:** 한 글자라도 바뀌면 알아챈다 |
| **사칭** | 가짜 서버가 진짜인 척한다 | **인증:** 인증서로 진짜 서버인지 확인한다 |

크롬은 2018년부터 HTTP 사이트에 "주의 요함"을 표시한다. 지금은 대부분의 사이트가 HTTPS를 쓴다.

### 연결 과정

![[https-연결-과정.svg]]

TLS 1.3 기준으로 간단히 나타내면 위와 같다.

1. **TCP 연결:** 먼저 [[osi-7계층#4계층-전송-계층|3-way handshake]]로 연결을 맺는다.
2. **ClientHello:** 클라이언트가 지원하는 암호 방식 목록과 키 교환 값을 보낸다.
3. **ServerHello + 인증서:** 서버가 암호 방식을 고르고, 자기 키 교환 값과 **인증서**를 보낸다.
4. **인증서 확인:** 클라이언트가 인증서가 믿을 만한 기관에서 발급됐는지, 도메인이 맞는지, 기간이 지나지 않았는지 확인한다.
5. **세션 키 계산:** 양쪽이 주고받은 키 교환 값으로 **같은 세션 키**를 각자 계산한다. 키 자체는 네트워크로 오가지 않아서 엿봐도 알 수 없다.
6. **암호화된 HTTP:** 이후의 요청과 응답은 모두 세션 키로 암호화된다.

### 두 종류의 암호를 섞어 쓰는 이유

| | 비대칭키 (공개키) 암호 | 대칭키 암호 |
| --- | --- | --- |
| 키 | 공개키와 개인키 한 쌍 | 양쪽이 같은 키 하나 |
| 속도 | 느리다 | 빠르다 |
| HTTPS에서 하는 일 | 처음 만날 때 **신원 확인과 키 교환** | 이후 **실제 데이터 암호화** (AES 등) |

대칭키 암호는 빠르지만, 처음에 그 키를 상대에게 안전하게 전할 방법이 문제다. 그래서 처음에만 비대칭키 방식으로 안전하게 세션 키를 맞추고, 실제 데이터는 빠른 대칭키로 암호화한다.

## 인증서

**인증서**는 "이 공개키는 정말 `example.com`의 것이다"라고 **인증 기관(CA)**이 서명해 준 전자 문서다.

### 신뢰의 사슬

```text
루트 인증서 (최상위 CA)       ← 운영체제와 브라우저에 미리 들어 있다
  └─ 중간 인증서 (중간 CA)
       └─ example.com 인증서  ← 서버가 보내준다
```

- 브라우저는 서버 인증서의 서명을 따라 올라가며 확인한다. 마지막에 **미리 믿기로 한 루트 인증서**에 닿으면 믿는다.
- 아무나 자기 인증서를 만들 수는 있다(자체 서명 인증서). 하지만 루트까지 이어지지 않으므로 브라우저가 경고를 띄운다.

### 발급과 기간

- **Let's Encrypt**는 2016년부터 인증서를 무료로, 자동으로 발급한다. HTTPS가 빠르게 퍼진 큰 이유다.
- 인증서에는 유효 기간이 있다. 업계 표준 기구(CA/브라우저 포럼)의 결정으로 최대 기간이 줄고 있다. 2026년 3월부터 200일이 됐고, 2029년까지 47일로 단계적으로 줄어든다. 키를 도둑맞아도 피해 기간을 짧게 하려는 것이다. 그래서 사람이 손으로 갱신하기보다 **자동 갱신**이 기본이 됐다.

## HTTPS가 지켜주지 못하는 것

주소창의 자물쇠는 **"이 서버와의 통신이 암호화됐다"**는 뜻이지, **"이 사이트가 안전하다"**는 뜻이 아니다.

| 착각 | 실제 |
| --- | --- |
| HTTPS면 믿을 만한 사이트다 | 피싱 사이트도 무료 인증서로 HTTPS를 쓴다. 도메인을 직접 확인해야 한다 |
| 어떤 사이트에 접속하는지도 숨겨진다 | 내용은 숨지만, 접속하는 **도메인 이름**은 연결 과정에서 보일 수 있다(SNI). 이를 숨기는 ECH 기술이 보급되는 중이다 |
| HTTPS로 받은 파일은 안전하다 | **원본 자체가 바뀌었으면** 소용없다. HTTPS는 오는 길만 지킨다 |
| 서버의 데이터도 안전하다 | 서버에 도착한 뒤의 일([[sql-인젝션]], 서버 해킹)과는 무관하다 |

세 번째의 예가 2026년 니케 PC 런처 사건이다. 런처는 공식 CDN에서 HTTPS로 스크립트를 받았지만, CDN에 올라간 파일 자체가 바뀌어 있었다. 통신은 안전했어도 받은 내용이 악성이었다.
이런 공격은 파일의 해시값을 미리 정해 두고 비교하는 **SRI**나 **코드 서명**으로 막는다. → [[owasp-top-10]]의 공급망 항목

## HTTPS를 제대로 쓰려면

- **HTTP로 들어오면 HTTPS로 보낸다.** 80번 포트 요청에는 301 리다이렉트로 HTTPS 주소를 알려준다.
- **HSTS:** 응답에 `Strict-Transport-Security` 헤더를 넣으면, 브라우저가 그 사이트에는 처음부터 HTTPS로만 접속한다. 첫 HTTP 요청을 가로채는 공격을 막는다.
- **혼합 콘텐츠를 없앤다.** HTTPS 페이지 안에서 이미지나 스크립트를 `http://`로 불러오면 그 부분이 암호화되지 않는다. 브라우저는 이런 스크립트를 막아 버린다.
- 쿠키에 `Secure` 옵션을 붙인다.

## HTTP와 HTTPS 비교

| | HTTP | HTTPS |
| --- | --- | --- |
| 기본 포트 | 80 | 443 |
| 암호화 | 없음. 내용이 그대로 보인다 | TLS로 암호화 |
| 서버 확인 | 없음 | 인증서로 확인 |
| 연결 속도 | TLS 핸드셰이크가 없다 | 처음에 핸드셰이크가 추가된다. TLS 1.3과 HTTP/2·3에서는 차이가 거의 없다 |
| 쓰는 곳 | 내부 테스트, 로컬 개발(`localhost`) | 사실상 모든 공개 서비스 |

## 직접 확인하기

- **[[크롬-개발자-도구]]:** 네트워크 탭에서 요청을 누르면 메서드, 상태 코드, 요청·응답 헤더가 모두 보인다. 보안 탭에서는 인증서와 TLS 버전을 볼 수 있다.
- **curl:** 터미널에서 실제 요청과 응답을 그대로 볼 수 있다.

  ```bash
  curl -v https://example.com        # 요청·응답 헤더와 TLS 과정까지 출력
  curl -I https://example.com        # 응답 헤더만 (HEAD 요청)
  ```
