## 토큰이라는 말

**토큰(Token)**은 원래 "표, 증표"라는 뜻이다. 놀이공원 입장 팔찌나 버스 토큰처럼 **"이걸 가진 사람은 이것을 할 수 있다"를 보여주는 물건**이다.

컴퓨터에서도 여러 곳에서 이 말을 쓴다. 같은 단어지만 뜻이 달라서 헷갈린다.

| 부르는 이름 | 뜻 | 예 |
| --- | --- | --- |
| **인증 토큰** (액세스 토큰) | 로그인했다는 증표 | Supabase 로그인 후 받는 JWT |
| **요청 토큰** (CSRF 토큰) | 이 요청이 정상 페이지에서 왔다는 증표 | 컴시간의 요청 토큰, 웹 폼의 숨은 값 |
| **API 토큰** | 프로그램이 서비스를 쓸 권한 | GitHub 토큰, 각종 API 키 |
| **AI의 토큰** | 글을 잘게 나눈 조각 | ChatGPT·Gemini의 "토큰 수" |

이 문서는 앞의 두 가지를 주로 다룬다.

## 인증 토큰

로그인하면 서버가 **"이 사람은 민수다"라는 증표**를 준다. 이후의 모든 요청에 이 증표를 붙여서 보낸다. 매번 비밀번호를 보내지 않아도 된다.

```http
GET /rest/v1/notice
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

`Bearer`는 "이것을 가진 사람(bearer)"이라는 뜻이다. **토큰을 가진 사람이 곧 그 사용자**로 취급된다. 그래서 토큰을 도둑맞으면 비밀번호를 도둑맞은 것과 같다.

### 세션과의 차이

로그인 상태를 유지하는 방법은 크게 두 가지다.

| | 서버 세션 | 토큰 (JWT) |
| --- | --- | --- |
| 로그인 정보를 기억하는 곳 | **서버**의 메모리나 DB | **토큰 자체**에 적혀 있다 |
| 사용자가 가진 것 | 세션 번호(아무 의미 없는 무작위 값) | 사용자 ID·만료 시각이 담긴 서명된 증표 |
| 요청이 오면 서버는 | 세션 번호로 저장소를 찾아본다 | 서명만 확인하면 된다 |
| 로그아웃 | 서버에서 지우면 즉시 끝 | 토큰이 만료될 때까지는 유효하다 |

- 토큰 방식은 서버가 아무것도 기억하지 않아도 돼서, 서버가 여러 대이거나 Supabase처럼 DB가 직접 확인하는 구조에 잘 맞는다.
- [[flask-세션|Flask의 기본 세션]]은 이름은 세션이지만 실제로는 서명된 쿠키에 내용을 담는다. 서버가 기억하지 않는다는 점에서 토큰 방식에 가깝다.

## JWT

**JWT(JSON Web Token)**는 가장 많이 쓰는 토큰 형식이다. 점(`.`)으로 나뉜 세 부분으로 되어 있다.

```text
eyJhbGciOiJIUzI1NiIs....eyJzdWIiOiJ1LTE3Iiwicm9sZSI6....SflKxwRJSMeKKF2QT4fw...
└────── 헤더 ──────┘ └────────── 내용 ──────────┘ └──────── 서명 ────────┘
```

가운데 내용 부분을 디코딩하면 이런 [[json|JSON]]이 나온다.

```json
{
  "sub": "u-17",              // 사용자 ID
  "role": "authenticated",    // 로그인한 사용자
  "exp": 1795000000           // 만료 시각
}
```

- 각 부분은 **Base64URL로 인코딩**만 되어 있다. 암호화가 아니라서 **누구나 내용을 읽을 수 있다.** 비밀번호나 개인정보를 넣으면 안 된다. → [[인코딩과-디코딩]]
- 대신 **서명**이 붙어 있다. 내용을 한 글자라도 바꾸면 서명이 맞지 않아 서버가 거부한다. 그래서 사용자가 `role`을 `admin`으로 고쳐도 소용없다. → [[대칭키와-공개키-암호#용도-2-전자-서명|전자 서명]]
- Supabase는 이 토큰의 `sub`를 꺼내 RLS 정책의 `auth.uid()`로 쓴다. → [[rls와-접근-제어]]

### 짧은 토큰과 긴 토큰

토큰은 로그아웃해도 만료 전까지 유효하다는 약점이 있다. 그래서 보통 두 개를 함께 쓴다.

| 토큰 | 유효 기간 | 하는 일 |
| --- | --- | --- |
| **액세스 토큰** | 짧다 (보통 1시간 안팎) | 실제 요청에 붙인다. 도둑맞아도 금방 쓸모없어진다 |
| **리프레시 토큰** | 길다 (며칠~몇 주) | 액세스 토큰이 만료되면 새로 받는 데만 쓴다. 서버에서 취소할 수 있다 |

Supabase 같은 라이브러리는 액세스 토큰이 만료되기 전에 리프레시 토큰으로 자동으로 새로 받아 준다. 사용자는 계속 로그인된 것처럼 느낀다.

### 토큰을 어디에 두나

| 저장 위치 | 위험 |
| --- | --- |
| 브라우저 `localStorage` | 페이지에 악성 스크립트가 끼어들면(XSS) 토큰을 읽어 갈 수 있다 |
| `HttpOnly` 쿠키 | 스크립트가 읽을 수 없다. 대신 CSRF를 막아야 한다 |
| 앱의 보안 저장소 | 안드로이드 Keystore, iOS Keychain. 앱에서는 가장 안전하다 |

## 요청 토큰 (CSRF 토큰)

**요청 토큰**은 "이 요청이 우리 페이지를 거쳐서 왔다"는 것을 확인하는 일회용 값이다.

1. 사용자가 페이지를 열면 서버가 무작위 값(토큰)을 페이지에 숨겨서 준다.
2. 페이지에서 요청을 보낼 때 그 토큰을 함께 보낸다.
3. 서버는 토큰이 맞는지 확인하고, 없거나 틀리면 거절한다(403).

### 왜 필요한가

원래 목적은 **CSRF(사이트 간 요청 위조)** 공격을 막는 것이다.

- 민수가 은행 사이트에 로그인한 채로, 공격자가 만든 다른 사이트에 들어간다.
- 그 사이트에 "은행으로 송금 요청을 보내는" 숨은 코드가 있다. 브라우저는 은행 쿠키를 자동으로 붙여서 요청을 보낸다.
- 은행 입장에서는 민수가 보낸 정상 요청처럼 보인다.

요청 토큰이 있으면 막힌다. 공격자의 사이트는 은행 페이지에 숨겨진 토큰 값을 알 수 없기 때문이다.

### 자동 수집을 막는 데도 쓴다

같은 원리로 **페이지를 거치지 않고 바로 데이터를 가져가는 프로그램**도 막을 수 있다.
2026년 11월 컴시간이 요청 토큰을 도입하자, 페이지를 열지 않고 데이터 주소로 바로 요청하던 스쿨헬퍼 첫 버전이 403으로 막혔다. 토큰을 만드는 스크립트는 난독화되어 있었고, 응답도 암호화됐다. 서비스가 자동 수집을 원하지 않는다는 뜻을 밝힌 것이다. → [[api-역공학#5-막혔을-때-기술적-보호-조치|기술적 보호 조치]]

## API 키와 토큰

| | API 키 | 인증 토큰 |
| --- | --- | --- |
| 누구를 나타내나 | 프로그램, 개발자 | 로그인한 사용자 |
| 유효 기간 | 보통 직접 지울 때까지 | 짧다 (만료됨) |
| 받는 방법 | 개발자 페이지에서 발급 | 로그인할 때마다 |
| 예 | NEIS 인증키, Gemini API 키 | Supabase 로그인 토큰 |

둘 다 **가진 사람이 곧 권한**이라는 점은 같다. 코드나 Git에 그대로 올리면 안 된다. → [[env로-api-키-관리]]

## AI의 토큰

AI 언어 모델은 글을 **토큰**이라는 조각으로 잘라서 처리한다. 영어는 대략 단어 하나가 1~2개 토큰이고, 한글은 글자 하나가 1개 이상의 토큰이 되기도 한다.
AI 서비스의 요금과 "한 번에 읽을 수 있는 길이"는 이 토큰 수로 정해진다. 로그인 토큰과는 전혀 다른 뜻이다.
